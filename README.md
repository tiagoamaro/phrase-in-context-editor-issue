# Phrase In-Context Editor vs Tailwind `hidden lg:block`

Minimal repro repository, spun out of an investigation into using Phrase's In-Context Editor.

**Bug:** Phrase's In-Context Editor scanner (`cdn.phrase.com/strings/plugins/editor/latest/ice/index.js`)
skips any element (or ancestor) whose class list literally contains the token `hidden`, via a static
`.matches('.hidden')` check — regardless of whether that class actually resolves to `display: none` at
the current viewport. Tailwind's `hidden lg:block` pattern (hidden below a breakpoint, visible at/above
it) is genuinely visible at desktop widths, but the scanner still sees the literal `hidden` token and
skips the whole subtree. The translation marker is left completely unprocessed.

Confirmed by Phrase support (Aug 11 2026): root cause is in `hidingClasses`'s
class-presence check, not something fixable via the `hidingClasses` config option.

**Load this page at a viewport ≥1024px (Tailwind's `lg` breakpoint).** Below that width all three
boxes are correctly hidden or shown per their own classes, and there's nothing to observe.

## Setup

Requires Node (`nodejs 24.12.0`, see `.tool-versions` — `asdf install` / `mise install` picks it up).

```sh
npm install
npm run build:css   # writes ./styles.css (committed, versioned — this is a static site, no build step at serve time)
npm run serve        # serves the repo root at http://localhost:4000
```

Or via `make`:

```sh
make up   # installs deps, watches src/input.css (rebuilds styles.css on change), serves at http://localhost:4000
```

Replace `accountId`/`projectId` in `index.html`'s `PHRASEAPP_CONFIG` with your real Phrase
values — the scanner script needs valid config to initialize.

Then open `http://localhost:4000/`.

`hidingClasses` is hardcoded to the vendor default (`["hidden", "visuallyhidden", "invisible"]`) —
per Phrase support's reply, dropping `"hidden"` from it has no effect on the victim case, since
that option isn't what drives this particular skip.

## What you should see

Three boxes, each wrapping a `{{__phrase_...__}}` marker:

1. **Control** — plain visible `div`, no hiding classes. Must get wrapped/made-editable by Phrase.
   If it doesn't, the integration itself is broken, not this bug.
2. **Victim** — `hidden lg:block`. Genuinely visible at ≥1024px because `lg:block` overrides
   `hidden` in the cascade. **Stays raw text (`{{__phrase_common.slogan__}}`) — this is the bug.**
3. **Expected-hidden** — bare `hidden`, no responsive override. Correctly hidden at every viewport.
   Phrase is *supposed* to skip this one — included so the claim stays scoped to "computed
   visibility vs. class-token presence", not "hidden should always be scanned".

The `#result` box at the bottom reports RAW vs wrapped/processed for each, ~3s after load.

To verify by hand: open devtools, inspect `#control` after Phrase has processed the page, note
the attribute/element it wraps processed markers in, then check `#victim` never gets it.

## Files

- `index.html` — the whole repro. Loads the real ICE script via the normal
  `window.PHRASEAPP_CONFIG` path, same as TC's `_phrase_ice.html.erb` layout partial (real Rails
  integration lives in the `tc` repo — this repo is intentionally Rails-free, since the bug is
  entirely client-side).
- `src/input.css`, `styles.css` — Tailwind v4 input/output. `styles.css` is generated by
  `npm run build:css` and committed, since this is a static site with no build step at serve time.
